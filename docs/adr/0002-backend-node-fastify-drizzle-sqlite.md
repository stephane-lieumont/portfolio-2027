# ADR-0002 — Backend: Node + Fastify + Drizzle + SQLite

- **Status**: Accepted
- **Date**: 2026-08-30

## Context

The portfolio needs a backend to enter projects and manage 3D visuals, instead of redeploying the site on every addition the way it worked in 2022.

The volume is tiny and will stay that way: a few dozen projects, a single author — Stéphane — and brochure-site traffic. No load, write-concurrency or high-availability constraints. The real constraint is **maintenance cost over time**: this project will live for years with months of not being touched, and it must not turn into a server to administer.

Stéphane works in .NET day to day at his job, and in Angular/TypeScript here.

## Decision

**Node 22 + Fastify + Drizzle ORM + SQLite** (`better-sqlite3`), in TypeScript, validated by Zod.

Node 22 runs TypeScript natively through type stripping: **the API has no build step**. `node src/server.ts` in development and in production alike. The tsconfig enforces `erasableSyntaxOnly` to guarantee the code stays compatible with that mode.

Migrations are generated by drizzle-kit and **applied at server startup**, in the `db` plugin.

## Consequences

One language across the whole repo. The Zod schemas in `@portfolio/shared-types` validate API input and type the Angular client — the same definition serves both ends. On a project run with AI agents, that single language also shrinks the surface to reason about.

SQLite has **no server to run**: the database is a file, and the backup is a file copy. On a personal project left dormant for months, that's decisive — there is no service to maintain, update or monitor.

No build step on the API: the Dockerfile copies the sources and starts. Fewer moving parts, less to break.

In exchange, we accept real limits: **a single concurrent writer** (moot here, with one author), **no replication and no horizontal scaling**, and a database tied to the container's filesystem — the volume must be persistent and backed up, or the data disappears with the container. The SQLite file never lives in the repository.

Drizzle sits closer to SQL than a classic ORM: you write more explicit queries than with EF Core, but you keep end-to-end typing and there's no binary engine to install.

Native type stripping rules out TypeScript enums, namespaces and constructor parameter properties. `erasableSyntaxOnly` checks for them at typecheck time, so the error surfaces while writing rather than at deploy.

## Alternatives considered

**.NET Minimal API + EF Core** — Stéphane's daily expertise, and a single-binary deployment. Rejected because it introduces a second language into a repo whose whole premise is sharing types between front and back: the contract would have had to be duplicated or generated, which is precisely what ADR-0001 sets out to avoid.

**NestJS** — the module architecture and dependency injection resemble Angular, which would have felt comfortable. Rejected for its boilerplate, out of all proportion for an API that exposes projects and media.

**PostgreSQL** — the default choice, and a real server to administer and back up in order to store a few dozen rows. The benefit-to-burden ratio doesn't hold up here. If the need changes, Drizzle keeps the switch reasonable.

**A headless CMS (Strapi, Directus, Payload)** — the admin interface comes for free, but you inherit an entire product to keep updated and a constrained data model, for a site that needs two entities.
