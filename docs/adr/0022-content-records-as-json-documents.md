# ADR-0022 — Content records stored as validated JSON documents, read by the build

- **Status**: Accepted
- **Date**: 2026-11-15 (amended the same day: media, tools and the Stack moved to tables)

## Context

Until now the site's projects and 3D pieces lived in a TypeScript file inside the Angular app (`core/data/static-content/static-content.ts`). ADR-0008 and ADR-0021 settled that the site is prerendered from the API, which therefore has to serve that content before V1 ships (issue #40). The back office that will edit it is V1.1.

The API's database held a provisional `projects` table written to prove the architecture: one column per field, a `sort_order`, a gallery join table. Spec 03 superseded it, and the content has kept moving since — client references with a logo instead of visuals, periods with a start and an ongoing end, a Google Play link, a dark logo plate on trial. Each of those was one field in a Zod schema and in the static file. In a column-per-field table each would also have been a migration, and every localized field (`{ fr, en }`, ADR-0017) would have been two columns or a JSON column anyway.

A `Project` and an `Artwork` are read whole: the site never asks for « every title » or « the projects using Docker ». What the API does query is small and stable: the kind, the publication status, the slug in each language, the release date.

## Decision

**Each dev project and each 3D piece is one row of a `works` table, the record itself stored as a JSON `document`.** The document is the shape `@portfolio/shared-types` defines (`projectSchema`, `artworkSchema`), validated by Zod when it is written and again when the API serves it. Beside it, the row keeps the columns the API filters and sorts on, written in the same statement as the document: `id`, `kind` (`dev` | `cgi`), `status`, `slug_fr`, `slug_en` (unique per kind and language), `released_at`, `published_at`, `created_at`, `updated_at`. A work names its images and its tools **by id** inside the document, never by key or slug.

**The public read routes** are `GET /api/projects`, `GET /api/artworks` and `GET /api/{projects,artworks}/:locale/:slug`, published records only, newest first, records released the same day in creation order; `GET /api/tools`, every tool with its icon resolved; and `GET /api/stack?domain=dev|cgi`, the world pages' Stack entries in their order, each with its tool resolved (both domains, dev first, without the parameter). Every response is sent with `Cache-Control: no-cache`, so a build run right after a publish never reads a cached list.

**Media, tools and the Stack are tables, with columns** (Stéphane, 2026-11-15, spec 04 §2). Unlike the works, their shape is small and settled, and the database can guard their references:

- `media_assets` holds every image the content uses: the renders and project visuals in the bucket, the client logos and the tools' marks in the web app's `public/`. **Only the metadata moved; the files stay where they are.** A row has a `purpose` (`render`, `cover`, `presentation`, `logo`, `mark`), a `storage` (`bucket` or `site`) and a `key` (an object key, or a root-relative path), its content type, intrinsic size, localized alt, average colour and a raster's WebP variants. The API resolves an asset id into exactly what the page rendered from the inline object before: `{ key, alt, width, height, averageColor }` for a bucket image, `{ src, width, height, variants, alt }` for a logo, `{ src, width, height }` for a mark. A reference to an asset of the wrong purpose fails like a missing one.
- `tools`: `slug` (unique), `label` `{ fr, en }`, `icon_id` → `media_assets`. No world: the same tool may serve both.
- `stack`: one row per tool shown in a world's Stack section, `tool_id` → `tools` with `ON DELETE RESTRICT`, `domain` (`dev` | `cgi`), `position`, and its « Maîtrise » points as **an ordered JSON array on the row** (`[{ strongLine, secondLine }]`, both localized), validated by `stackEntryRecordSchema` from shared-types, rather than a child table: the points are read and edited only with their entry. `(tool_id, domain)` is unique.
- **Works reference tools by tool id**, so renaming a slug breaks nothing; the API resolves each id into `{ id, slug, label, icon }`. Deleting a tool still in use is refused: the Stack by its foreign key, the works by `deleteTool` (`src/db/tool-usage/`), which finds the tool in the documents with `json_each` and returns where it is used (`toolUsage`), for the back office to say so.

**What V1.1's upload (#55) adds**: the API receives the file, checks its type and size, writes it to the bucket, derives the variants and inserts the `media_assets` row, `byte_size` included (null for the seeded rows, whose files the seed never reads). A logo or a mark uploaded then lives in the bucket like a render; the `site` storage remains for the files already in `public/`.

**The seed is the content's only source until the back office.** `apps/api/src/db/seed/` holds the records (`media.ts`, `tools.ts`, `stack.ts`, `content.ts`, which name each other's rows through `mediaId(key)` and `toolId(slug)`); `pnpm --filter @portfolio/api db:seed` validates every one and follows every reference before writing any (`resolveContent`, the same resolution the API serves), then upserts them by id, media first: a new record is inserted published, a record whose document changed is rewritten and published, and an unchanged one is left as it is, status and `updated_at` included. Running it twice changes nothing.

**The site reads the API before its build.** `apps/web/scripts/content.mjs` fetches the works, the tools and the Stack from `CONTENT_API_URL` (default `http://localhost:3000`) and writes `core/data/content/content.generated.ts`, gitignored, which the app imports exactly as it imported the static file. An unreachable API fails the build. The tests, the typecheck and `ng serve` write the same file from the seed instead (`--seed`), resolved by the API's own `resolveContent`, so they need no server. `pnpm build:site` seeds a temporary SQLite file, starts the read routes alone on it (`src/content-server.ts`, which needs neither MinIO nor SMTP), builds the site and stops the server; `pnpm verify` ends with it, locally and in CI.

## Consequences

- A new content field is a schema change and nothing else: no migration, no column. The table only changes when the API needs to filter or sort on something new.
- The same Zod schema guards the seed, the database's output and, in V1.1, the back office's input. A stored document that no longer meets it makes the API answer 500 and the build fail, rather than reach a page.
- The site's pages are what they were from the static file: the generated module has the same shape and the app reads it synchronously, so no component or route changed beyond its import. Measured on the 56 prerendered pages, they differ from `main`'s only by bundle hashes and hydration template ids, which also differ between two builds of the same code.
- **Measured after the amendment**: the 58 prerendered pages still match `main`'s once bundle hashes, the order of the `modulepreload` links and the hydration template ids are set aside.
- **A work's references to media and tools are not foreign keys.** They live inside JSON, so SQLite cannot refuse a dangling one; the seed refuses it before writing, the API answers 500 rather than serve it, and `deleteTool` checks before deleting. V1.1's media deletion needs the same check, not written yet.
- **A tool has no world any more.** The rule that the two vocabularies never mix (spec 03) is now editorial: nothing stops a dev project crediting ZBrush.
- **Stack positions are not unique in the database.** A reorder written row by row would collide mid-way under a unique index; the seed checks them instead, and V1.1 must write a reorder in one transaction.
- **The seed's media metadata can drift from the files.** Sizes and keys are typed in `seed/media.ts`; the site's tests check that every mark file exists, not that its size is right.
- **Querying inside the document is awkward.** « Every project using Angular » means `json_each` over every row or loading them all. At a few dozen records loading them all is instant; if a real need appears, the value becomes a column beside the document, kept in step by the code that writes both.
- **The document's shape has no migration.** Renaming or restructuring a field means rewriting the stored documents in a script, and until then they fail validation on the way out. Adding an optional field costs nothing; anything else is a data migration written by hand.
- **The columns duplicate the document.** Slugs, kind and release date exist twice and are only consistent because every write goes through the code that sets both. V1.1's write routes must keep that invariant; nothing in SQLite enforces it.
- **Order within a day is creation order.** Most pieces are dated by their year only, and the mosaic's order among them is editorial. Spec 03 forbids a sort field, so the API orders ties by the table's `rowid`: the seed's order on a fresh database. A record re-created later goes after its peers; the V1.1 back office will need a deliberate answer if Stéphane wants to reorder within a year.
- **The seed republishes what it rewrites.** Once V1.1 can unpublish a record, reseeding a database with a changed copy of it would publish it again: the seed is for a fresh environment from then on, not for production. Its change detection compares the stored JSON text, which only holds while every writer serialises in the schema's key order.
- **The seed does not delete.** A record removed from the seed file stays in a database that already holds it; removing it is a manual `DELETE` until the back office exists.
- **The build now depends on the API,** locally too: `pnpm --filter @portfolio/web build` alone fails unless an API answers at `CONTENT_API_URL`. `pnpm build:site` is the one-command path. The tests read the seed, so a content edit that breaks a content check fails `pnpm verify` before the build.
- In V1.1 the database becomes the source and the seed file a fixture for the tests and for a fresh environment; at that point it will drift from production, and that is expected.

## Alternatives considered

- **One column per field, as the provisional schema had.** Real SQL queries on every field and constraints in the database. Rejected: every field the content has gained this autumn would have been a migration, localized fields double the columns, and nothing in the site queries by field. The constraints that matter are cross-field (a logo or a presentation, never both) and live in Zod anyway.
- **Two tables, `projects` and `artworks`, as spec 03's two entities.** Rejected for now: both rows would have exactly the same columns, and one table keeps one upsert and one ordering rule. The two entities stay distinct where it matters, in two schemas and two route sets.
- **Angular's prerender fetching the API with `HttpClient`, and `TransferState` for the browser.** No generated file. Rejected: the routes, the language switch and the mosaic read the content synchronously, so every one of them would have to wait on a store; and `TransferState` writes the data into each page's HTML, which would have changed every page and grown each by the whole catalogue.
- **The seed as a JSON file exported from the TypeScript content.** Rejected: the content's provenance notes (« only the open-source stack », where a year comes from) are comments, and JSON has none. A typed TypeScript file is checked against the schema types by the API's typecheck as well.
- **Keeping the static file in the app as a fallback when the API is down.** Rejected by ADR-0008: a build from a second copy would ship content the API no longer holds, silently.
